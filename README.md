# 岛屿（Island）

> 项目定位：一个原生 Android APK 内的 AI-Native「小手机」与角色陪伴世界。  
> 当前阶段：产品设计与原生桌面 MVP 规划。  
> 文档语言：简体中文。  
> 技术方向：Kotlin + Jetpack Compose；不使用 WebView/H5 套壳作为主界面。

## 1. 岛屿是什么

「岛屿」不是一组彼此独立的 AI 聊天小工具，而是一部能被 user 使用、由多个 char 共同生活、成长和留下记录的虚拟手机。用户可以在桌面上打开 21 个应用；聊天、日程、相册、备忘录、角色成长、论坛、情侣空间等应用通过同一套角色资料、事件记录、记忆系统和权限设置进行双向联动。

核心体验：

- **角色有生活**：char 可以有日程、所在城市、天气、朋友圈/论坛动态、日记、相册和阶段性成长。
- **互动有连续性**：一次聊天中的约定，经用户允许后，可以进入日历、闹钟、倒数日、情侣空间或成长时间线。
- **记忆有来源**：重要回忆能够追溯至原始消息或事件，支持更正、确认、遗忘与分支隔离，而不是只依赖一段越写越长的提示词。
- **剧情有边界**：主线聊天、相遇、番外笺、栖迟可使用不同的剧情分支与记忆策略，避免 IF 线污染主线。
- **本地优先**：桌面布局、图标、角色资料、日记、日历、聊天记录和媒体元数据优先保存在本地；外部 AI、天气、音乐等服务按需启用。

## 2. 技术与产品边界

### 2.1 原生 APK

- 使用 Kotlin、Jetpack Compose、Material 3 和单 Activity 架构。
- 使用原生 Compose 页面与触控交互，不使用网页套壳实现主要 UI。
- 第一阶段做**岛屿应用内部的虚拟手机桌面**，不是接管系统桌面的 Launcher。后续若真要成为系统默认桌面，应单独评估 Launcher、系统兼容性和权限。
- 首页网格为 4 列 × 6 行；底部 Dock 单独布局，不占 6 行网格。
- 所有首页图标使用项目内透明 PNG 静态资源，运行时不依赖远程图标 URL。

### 2.2 手机端开发路线

推荐工作流：

1. 在手机浏览器或 GitHub App 中创建/管理仓库。
2. 在 Claude 中连接仓库并使用云端编码会话（若账号功能可用）；也可以让 Claude 生成单个任务的代码，再按文件提交。
3. 通过 GitHub Actions 或兼容的云端环境运行 Gradle 构建，产出 Debug APK。
4. 将 APK 下载到手机安装测试；每完成一个小任务就提交一个 Git commit。

说明：手机可以完成仓库管理、提示词编写、云端构建和 APK 测试，但屏幕较小，排错会比电脑困难。云端构建是否可用取决于仓库配置、运行额度和服务权限。不要把“只用手机”误解为手机本地一定能直接运行完整 Android Studio。

### 2.3 技术栈建议

具体依赖版本需在开始编码时核对 Android 官方文档并采用兼容的稳定版本，禁止为了追新随意升级。

- UI：Kotlin + Jetpack Compose + Material 3
- 导航：Navigation Compose
- 状态：ViewModel + StateFlow，遵循单向数据流
- 本地数据库：Room
- 简单设置：DataStore
- 网络：Retrofit/OkHttp 或一个统一且明确的网络层
- 图片加载：Coil（远程图需要时）；本地图片使用 Android Photo Picker/系统文件选择器
- 后台任务：WorkManager；只有明确需要准时触发的用户闹钟，才评估 AlarmManager 与相应权限
- 测试：JUnit、Compose UI 测试；每个任务至少运行可用的构建或测试
- 构建：Gradle Wrapper + GitHub Actions（使用仓库中的 Gradle Wrapper，不依赖开发者本地安装 Gradle）

首期先使用**单个 Android app module + 按功能分包**，避免初学阶段就引入复杂多模块工程。功能边界稳定后再考虑拆模块。

## 3. 桌面与布局规范

### 3.1 主页一（4 × 6）

网格位置采用 `row=1..6`、`column=1..4` 表示。组件会占据多个格子，不能与图标重叠。

| 元素 | 尺寸 | 默认位置 | 说明 |
|---|---:|---|---|
| 日历组件 | 4 × 2 | 第 1–2 行，整行 | 左侧圆角图片区域，可选本地图片；右侧实时月历 |
| 音乐唱片组件 | 2 × 2 | 第 3–4 行，第 1–2 列 | 无可见卡片底色、边框或分割线；唱片/播放状态动画 |
| 纪念日组件 | 2 × 2 | 第 5–6 行，第 3–4 列 | 两个圆头像；显示“在一起 xxx 天”；头像可从本地导入 |
| 8 个 APP 图标 | 每个 1 × 1 | 第 3–4 行右半区、第 5–6 行左半区 | 对应：屿年、相册、日历、备忘录、天气、时钟、设置、电话 |

主屏幕组件可选择背景图时，应存储图片 URI/本地副本并处理失效情况；不应将用户选图强制上传到服务端。

### 3.2 主页二（4 × 6）

| 元素 | 尺寸 | 默认位置 | 说明 |
|---|---:|---|---|
| 照片组件 | 2 × 2 | 第 1–2 行，第 1–2 列 | 正方形照片，无额外边框和卡片底色 |
| 天气组件 | 2 × 2 | 第 3–4 行，第 3–4 列 | 今日/明日/后日天气与今日温度；支持本地背景图；定位需获得用户授权或允许手动设定地点 |
| INS 风格消息组件 | 4 × 2 | 第 5–6 行，整行 | 两条黑灰色圆角气泡（约 `#272727`），文字白色；左右各一条 4dp 深灰竖条，垂直居中，竖条比气泡高度矮约 4dp |
| 9 个 APP 图标 | 每个 1 × 1 | 预期剩余区域 | 对应：倒数日、关联账号、论坛、文学城、情侣空间、音乐、番外笺、美团、栖迟 |

**需要明确的网格冲突：** 当前三个组件共占 16 格，剩余只有 8 格，但该页列出 9 个独立图标。因此不可能在保持组件位置、4 × 6 网格及每个 APP 独占 1 格的同时，把 9 个图标全部放进剩余格子。

**默认实现决策：** 保留 9 个独立 APP 模块和 21 张独立图标资源；主页二先显示 8 个固定图标，第 9 个可从“全部应用”抽屉访问。桌面原型完成后再开放“文件夹 / 调整组件位置 / 增加第三页”配置，不得用重叠图标或缩小格子等方式偷偷绕过冲突。以后如用户明确选择了其他方案，应以用户最终决策为准。

### 3.3 Dock 与桌面操作

Dock 固定有 4 个应用：聊天、相遇、世界书、预设。它不计入 4 × 6 网格。

- 左右滑动切换两页桌面。
- 长按桌面空白处约 1 秒，进入编辑模式。
- 长按图标或组件也可进入编辑/拖动状态。
- 图标、组件与 Dock 项目均能拖动；必须有拖动预览、合法目标高亮、碰撞检查、取消操作与保存反馈。
- 不允许组件重叠或覆盖图标。拖动到被占用的多个格子时，需要明确采用交换、推开或提示不可放置其中一种规则，且在整个项目中一致。
- 布局持久化；重启应用后位置不丢失。
- Dock 最多 4 个位置，不能把桌面元素拖进 Dock 后导致原 Dock 项目无处存放。
- 编辑模式有明显的“完成”按钮，并支持撤销最近一次布局调整。

## 4. 应用清单与页面草图

以下是产品目标，不代表所有模块已经实现。开发计划按小任务分期实现。

### 4.1 主屏幕第一页的应用

1. **屿年**：char 的成长年表、年龄/人生阶段、学业与工作阶段、里程碑、未来计划和时间线快照。重大成长事件需能追溯来源，用户可以批准、编辑或撤回不合适的生成结果。
2. **相册**：按 char 分册；支持导入本地照片、保存聊天片段/截图、保存 char 生图、查看图片来源与时间、收藏、标签、搜索。聊天中收到/发送图片时可选择保存到相应 char 的相册。
3. **日历**：月/周/日视图；记录 char 日程、user 与 char 的共同约定、生日和纪念日。日程可来自 AI 建议，但写入正式日历前应展示确认操作或遵循用户配置的自动写入规则。
4. **备忘录**：user 笔记、日记、清单；char 的碎碎念、日记及与 user/家人/朋友有关的笔记；支持标签、搜索、时间、关联 char 和记忆作用域。可选择是否将笔记作为 AI 记忆来源。
5. **天气**：显示 user 或 char 指定地点的天气与温度；支持手动地点和经授权的真实位置。角色所在地与 user 所在地是两种不同配置，不要混为一谈。
6. **时钟**：闹钟、提醒、计时器；可将聊天中的约定转为待确认提醒。系统是否准时触发取决于 Android 权限、系统节电规则和用户设置，必须如实显示权限状态。
7. **设置**：外部 API 配置、流式/非流式输出偏好、模型参数、图像/语音服务、通知、隐私、数据备份、外观、记忆策略、调试信息与用量查看。
8. **电话**：可先做 char 语音通话 UI、通话记录、时长、摘要与收藏；后续再研究真实号码/拨号。不能把模拟通话描述为已接入真实电话网络。

### 4.2 主屏幕第二页的应用

1. **倒数日**：纪念日、目标日、已过去天数、周年提醒与通知。
2. **关联账号**：在岛屿内为 user 和 char 建立明确的关联关系；可选择共享的聊天通知、动态、日程或账号可见范围。访问记录需透明、可撤销，不能暗中读取设备外部账号。
3. **论坛**：char 与 NPC 的动态流、帖子、评论、点赞、关注、话题、时间线和内容生成设置。自动发帖可设置频率、安静时段、审核方式和暂停开关。
4. **文学城**：同人文/小说创作、章节管理、角色视角、风格、世界观、连载与发布草稿；可以引用世界书和明确授权的记忆。
5. **情侣空间**：与一个 char 建立双方确认的关系空间；便利贴、每日问候、共同日历、纪念日、回忆墙、共同任务、照片交换与关系里程碑。断更后使用温和的“重燃火花”机制，不用惩罚式清零制造压力。
6. **音乐**：先支持本地音乐、播放列表与 LRC 歌词；后续再评估官方授权/可用的在线音乐接入方案。第三方非官方接口可能随时失效或有合规限制，不应作为首期必须依赖。
7. **番外笺**：独立 IF 线/番外剧情、长篇剧场、可选文风与剧情分支。默认不写入主线聊天、相遇或全局记忆；只有明确的“提取为主线记忆”功能才可跨出边界，且默认关闭。
8. **美团（暂定名）**：首期定位为虚构生活模拟页面，可模拟菜单、虚拟下单、团购与订单进度。真实平台下单、真实门店信息、支付与配送需要独立评估授权、合规、接口和支付安全，不假设能仅靠 UI 实现。
9. **栖迟**：char 梦境/文游体验；选择项、多结局、梦境生成、回看与重玩。每个梦境有独立分支，可在生成前选择“仅作梦境”或“允许提取为记忆”。

### 4.3 Dock 应用

- **聊天**：主功能，提供 char 私聊、消息列表、联系人、动态/朋友圈、我/个人中心、聊天设置、API 与记忆控制。
- **相遇**：线下见面风格的长篇剧情/场景互动，支持旁白、动作描写、文风预设与可选记忆提取；与普通聊天共享角色资料，但剧情分支和记忆写入策略要单独配置。
- **世界书**：管理角色背景、地点、人物关系、世界规则、触发条件与优先级，供提示词组装器检索注入。
- **预设**：管理可排序、可开关、可创建的系统提示词模块与输出格式。用户可以选择线上聊天、相遇、论坛、文学城或栖迟使用哪些模块。

## 5. 聊天模块详细规划

### 5.1 建议的一级页面

- **消息**：最近会话、未读计数、置顶、搜索、草稿、按 char / 群聊 / 系统通知分类。
- **联系人**：char 列表、NPC 列表、关系标签、搜索、分组、角色卡导入/导出、创建/归档 char。
- **动态**：char 与 NPC 发布的动态；支持图片、文字、评论、点赞；内容可链接到对应的角色、日程或事件，但需遵循主线/IF 线范围。
- **我**：user 人设、头像、个人偏好、隐私、API 状态、数据备份/导出、用量、通知与外观设置。

### 5.2 私聊界面

首期最小可用功能：

- 文本消息、流式输出、发送中/失败/重试状态、停止生成。
- 角色头像、消息时间、复制、编辑后重发、重新生成、继续生成、删除本地消息。
- 图片/语音等消息类型使用统一的消息模型，即使相关 API 尚未接入，也要显示明确的“未配置/暂不可用”状态，不伪装成功。
- 会话内搜索、书签/收藏、引用回复、消息分支、导出记录。
- “记为重要”“加入备忘录”“添加到日历”“保存到相册”“提取为成长事件”等显式动作。
- 显示当前使用的 char、剧情分支、预设、记忆范围与 API 提供方，便于排错。

### 5.3 私聊设置子页面

- **模型与输出**：API 提供方、模型名、接口地址（可选）、流式/非流式、温度等模型参数、超时与最大输出长度。
- **提示词**：当前预设、提示词模块顺序、启用/禁用模块、上下文长度策略。
- **记忆**：最近消息窗口、摘要频率、重要记忆开关、向量检索开关、角色/分支作用域、记忆写入审核规则。
- **角色行为**：主动消息频率、主动日程、动态生成、安静时段、是否需要 user 确认。
- **外观**：主题、气泡、字体大小、聊天背景、打字动画。
- **数据管理**：导出、清空、撤销记忆、重建摘要。危险操作必须二次确认。

## 6. 核心架构：让 APP 真正双向互通

不要让每个 APP 自己保存互不相干的“角色副本”。角色、事件、消息、记忆、图片元数据和关系应有统一的本地数据源；各 APP 是不同的展示界面和操作入口。

### 6.1 共享数据对象建议

- `Character`：角色 ID、名称、头像、角色卡、当前状态、所在地、时区、关系与配置。
- `Conversation` / `Message`：会话、消息内容、消息类型、时间、状态、所属角色、剧情分支。
- `StoryBranch`：主线、相遇分支、番外线、梦境线等；每项数据明确其 branch/scope。
- `DomainEvent`：事情发生了什么、发生时间、参与者、来源 APP、来源消息/文件、分支、隐私等级、是否确认、是否已处理。
- `MemoryItem`：事实/事件/偏好/摘要、来源 ID、置信度、有效时间、创建时间、最后确认时间、作用域、可撤销状态。
- `MediaAsset`：本地 URI、媒体类型、来源（导入/生成/聊天保存/截图）、所属角色、来源消息、创建时间、标签。
- `CalendarEntry` / `Reminder` / `Relationship` / `ForumPost` / `Note` / `CoupleSpaceEntry`：由统一角色与事件 ID 连接，而不是复制角色资料。

所有跨 APP 事件应带 `eventId`、`sourceApp`、`createdAt`、`branchId`、`scope` 和幂等标记，防止一个事件重复写入，或 A 更新 B、B 又反过来重复更新 A。

### 6.2 双向互通矩阵

“互通”既包括 A 的操作更新 B，也包括 B 产生的新内容返回 A。实际写入前遵循用户权限与剧情分支设置。

| APP A ↔ APP B | A → B | B → A |
|---|---|---|
| 聊天 ↔ 日历 | 从聊天约定中建议生成日程 | 日程到期、变更或天气冲突可进入聊天提醒/对话上下文 |
| 聊天 ↔ 备忘录 | 用户/char 可把消息保存为笔记 | 相关笔记可在聊天中检索；主动引用前展示来源 |
| 聊天 ↔ 相册 | 聊天图片或选中的聊天片段可存入角色相册 | 相册图片可作为聊天附件或经授权作为回忆线索 |
| 聊天 ↔ 屿年 | 已确认的重大事件可成为成长里程碑 | 当前人生阶段与成长目标可影响角色规划和聊天表达 |
| 聊天 ↔ 天气 | 聊天中确认的角色所在地可更新角色地点配置（需确认） | 实时/缓存天气可用于聊天场景，不可伪称实时数据 |
| 聊天 ↔ 时钟 | “明天提醒我”等语句可提出提醒草稿 | 闹钟触发后生成通知，用户可选择回到会话 |
| 聊天 ↔ 倒数日 | 对话中可提出纪念日草稿 | 临近周年提醒可以进入聊天或情侣空间 |
| 聊天 ↔ 电话 | 发起语音会话并保存通话记录 | 通话摘要/收藏内容可选择写入聊天记忆 |
| 聊天 ↔ 世界书 | 可从消息选取新事实作为世界书草稿 | 命中世界书条目后给聊天提示词提供背景 |
| 聊天 ↔ 预设 | 对当前会话选择专用预设 | 预设控制模型输出与记忆提取格式，变更应可预览 |
| 聊天 ↔ 相遇 | 共享角色基本资料，可选择携带部分主线摘要 | 相遇事件可由 user 选择提取到主线聊天 |
| 聊天 ↔ 番外笺 | 只能显式复制角色设定；默认不共享剧情记忆 | 默认不把番外内容写入聊天；显式“转正史”才可提取 |
| 聊天 ↔ 栖迟 | 可把当前情绪/事件作为梦境生成素材（按选项） | 梦境默认独立；允许提取时只选用户确认的事件 |
| 聊天 ↔ 论坛 | char 可从已经确认的生活事件生成动态草稿 | 论坛评论/回复可进入角色社交事件或聊天上下文 |
| 聊天 ↔ 文学城 | 角色卡、世界书和授权记忆可用作小说素材 | 小说可提取人物关系/新设定草稿，不能未经确认改写正史 |
| 聊天 ↔ 情侣空间 | 可将问候、约定、合照建议转成情侣空间事项 | 共同日记、便利贴或纪念日可被授权用于聊天 |
| 聊天 ↔ 关联账号 | 在授权范围内模拟跨角色账号收件箱/可见通知 | 其他已关联角色消息可显示到会话入口，但必须保留发送者和权限来源 |
| 日历 ↔ 时钟 | 日程可设置提醒 | 提醒可打开对应日程，延后/完成状态回写日历 |
| 日历 ↔ 天气 | 日程关联地点后获取天气参考 | 恶劣天气可建议调整计划，不应擅自改期 |
| 日历 ↔ 屿年 | 学业、入职、升职等时间节点可形成里程碑 | 成长目标可提出未来规划草稿，需确认后写正式日历 |
| 相册 ↔ 论坛 | 选定照片可附到动态草稿 | 动态中的图片可选择存档到角色相册 |
| 备忘录 ↔ 屿年 | 重要笔记可转为成长事件候选 | 成长时间线可链接原始笔记或日记 |
| 倒数日 ↔ 情侣空间 | 情侣纪念日可创建倒数日 | 周年奖励/回忆墙可链接同一纪念日，不维护两份日期 |
| 音乐 ↔ 聊天 | 正在播放的曲目可作为可选聊天上下文 | 聊天提及的歌曲可加入播放列表草稿（若有本地曲库） |
| 关联账号 ↔ 论坛/日历/相册 | 经授权共享动态、日程或相册条目 | 角色登录模拟页面后的查看行为可产生可见记录，权限随时可撤回 |
| 预设 ↔ 世界书 | 模块可设定世界书检索规则 | 世界书命中信息按预设指定顺序注入上下文 |
| 栖迟/番外笺/相遇 ↔ 记忆中心 | 各分支只提交候选记忆，并带上 branch ID | 记忆中心按权限决定隔离、摘要或提取，默认不跨线污染 |

这张矩阵是设计契约，不是要求首期一次实现。开发计划会先实现一条完整的“消息 → 事件 → 日历/备忘录 → 再回到聊天”的闭环，再按同一机制扩展其他 APP。

## 7. 记忆系统设计建议

向量检索只是记忆系统中的一个召回器，并不等于长期记忆本身。建议分层实现：

1. **原始记录层**：保留聊天消息、日程、笔记等来源记录；源数据不被 AI 摘要覆盖。
2. **事件层**：将“答应周五一起去海边”“换工作”“第一次见面”等事件保存为结构化事件，记录时间、参与者、来源和剧情分支。
3. **重要事实层**：角色身份、偏好、关系约定、长期目标等；区分 user 确认、模型推断、待确认三类。
4. **短期上下文层**：最近 N 条消息、当前场景与会话摘要。
5. **长期摘要层**：按角色和分支保存可更新的时间线摘要，摘要必须能回溯原始来源。
6. **语义检索层**：后续接入 embedding/向量检索，以语义相似度召回候选记忆；同时保留关键词、时间、角色、分支筛选。不能只靠向量相似度决定事实真伪。
7. **冲突与纠错层**：新旧记忆冲突时记录冲突、时间与来源，优先依据用户确认和事实有效期；无法判断时询问 user。支持更正、撤销和查看“AI 为什么记得这件事”。

每个记忆条目至少保存：`id`、`characterId`、`branchId`、`scope`、`content`、`type`、`sourceIds`、`confidence`、`createdAt`、`validFrom/validTo`（适用时）、`userConfirmed`、`status`。

建议首期先把 Room 中可追溯的结构化记忆、手动标记重要消息和摘要做可靠，再做向量检索。避免第一版就把复杂向量数据库当作项目地基。

## 8. 预设与提示词组装器

预设应是有 ID、名称、内容、启用状态、排序号、适用场景与作用域的模块列表。用户可添加/删除/排序自己的模块，但应用必须保留一个可恢复的默认预设。

目前用户提出的默认候选顺序：

1. 世界书最高
2. 世界书前
3. char 人设
4. 深度理解 char 人设的说明
5. user、char、NPC 关系网
6. user 人设
7. 重要记忆
8. “鱼的记忆”（用户自定义术语，具体定义待用户补充，不要擅自解释）
9. 模糊记忆
10. 短期记忆/向量记忆（需在 UI 中拆成可独立排序的模块）
11. 世界书中
12. 生成日程/写入提示词
13. 世界书低
14. 跨 APP 记忆
15. 输出格式（文本、语音、图片、转账等消息类型；仅为格式规划，不表示已接入支付/语音等服务）
16. 时间感知（当前时间、时区、季节、天气数据来源与更新时间）
17. 今日行程感知
18. 内部推理/输出前自检策略
19. 对话上下文

“思维链”建议在实现时改写成**内部推理/输出前自检策略**：不要求模型向用户展示私密的逐步推理。默认顺序只是起点，需允许用户排序、禁用和创建模块；不同 APP 可以配置不同预设。注入文本需要有 token 预算、优先级和裁切策略，不能不加限制地无限拼接。

## 9. API 与外部依赖规则

- API 配置应按用途分组：聊天生成、日程生成、论坛/动态生成、小说生成、梦境生成、生图、语音、天气等。
- 每个 Provider 实现统一接口，并声明是否支持流式响应、可用模型、输入/输出类型与限制。不能假定所有服务都支持流式输出或图片/语音。
- API key 不得写进源码、默认配置文件、README、截图或 GitHub 提交记录；禁止把密钥打印到日志。个人本地使用可在应用设置中输入密钥并安全保管；若将来对外发布，多用户产品应优先采用受控后端代理和配额机制。仅存在 APK 内的密钥无法被视为绝对保密。
- 服务未配置、请求超时、网络断开、额度不足、格式不匹配时显示可理解的错误和重试入口。不要用假数据伪装成功响应。
- 天气数据必须展示地点与更新时间；定位前请求权限，拒绝后可手动选地点。
- 音乐在线播放、真实外卖、真实通话等不可只凭 UI 完成；先实现本地或模拟体验，再单独评估官方 API、授权、合规和安全。

## 10. 情侣空间玩法灵感

优先选择能长期自然使用、无惩罚压力的互动：

- **每日双向留言**：两边可各留一张便利贴/一句话，支持延迟送达、回看与收藏。
- **共同时间胶囊**：共同写下一个问题或愿望，约定未来某天开启。
- **双人小日历**：纪念日、共同计划、下一次“约会剧情”与照片回忆可相互链接。
- **心情天气**：双方选一个天气/颜色表达今日状态；不需要连续打卡也不会惩罚。
- **共同相册与回忆地图**：为每张图片加时间、地点（可选）和相关聊天片段。
- **每周小问题**：诸如“这周最想收藏的瞬间”“下次想一起尝试什么”；可设置轻松跳过。
- **陪伴任务**：共同听一首歌、写一段故事、互相推荐一本书、一起整理回忆；完成记录可加入回忆墙。
- **共同房间/小岛**：随着关系里程碑解锁可摆放的家具、植物、照片墙和主题装饰，装饰资源可先全部本地化。
- **周年档案**：把过去一年确认过的文字、照片、日历事件生成年度册，先预览再保存。
- **重燃火花**：中断后不清零。允许选择“从今天重新开始”“补写一段近况”“共同完成一个小任务”，并保留之前历史。
- **纪念奖励**：可解锁专属主题、语音信件、共同剧情章节、相册边框或年度回忆册；奖励重点放在内容与回忆，不设计逼迫付费/连续签到的机制。

## 11. 清单外值得考虑的功能

1. **记忆中心**：集中查看每个 char “记住了什么、来自哪里、确认状态如何”，允许修正错误和设置有效期。
2. **岛屿收件箱/通知中心**：统一展示日程提醒、周年、char 留言、论坛互动和系统错误；点击可回到来源 APP。
3. **角色状态卡**：当前地点、今日安排、心情/精力（若启用）、正在做什么、最近事件；数据要标注是实际数据、AI 生成还是模拟状态。
4. **关系图谱**：user、char、NPC、家庭与朋友之间的关系可视化；修改关系时记录来源和时间。
5. **剧情分支管理器**：显示主线/IF/梦境/相遇各自的记忆写入策略，并支持从某个节点分叉和回滚。
6. **数据备份与迁移**：角色卡、预设、世界书、文字记录和布局可导出为可读格式；媒体可另行打包。敏感密钥默认不跟着导出。
7. **API 与用量面板**：按功能统计请求次数、耗时、失败原因和可测算的消耗；日志不得保存密钥或不必要的敏感内容。
8. **安静时段与自主行为控制台**：集中控制 char 是否能主动发消息、发动态、生成日程或写笔记，设定频率、暂停和审核策略。
9. **来源追溯卡**：点击记忆/日程/动态，可以查看它引用了哪几条聊天、哪次生成、是否由 user 确认。
10. **安全恢复**：崩溃后的草稿恢复、数据库迁移备份和“导出数据后重置”。这些基础能力比早期增加更多 AI 花活更重要。

## 13. 当前明确的非目标

- 首期不实现真实外卖支付或真实订单配送。
- 首期不宣称有真实蜂窝语音电话；先做应用内通话体验与记录。
- 首期不假设网易云音乐有可直接使用的官方开放接口，也不依赖不稳定的非官方接口。
- 首期不构建完整的多用户云同步/公开社交后端；先打好本地数据模型和 API 抽象。
- 首期不一次性实现全部 21 个 APP 的完整功能，先交付桌面和一条闭环联动。
- 首期不把所有 IF、梦境和相遇内容无条件混入主线记忆。

## 14. 建议的首期验收目标

首个可安装 MVP 应完成：

- 原生 APK 可以构建并安装；没有网页套壳。
- 短动画/启动页能进入桌面，网络失败不妨碍打开本地桌面。
- 两页 4 × 6 虚拟桌面、左右滑动、21 个本地 PNG 图标资源、4 个 Dock 图标和基础组件布局。
- 长按进入编辑态，图标/组件移动后布局可以持久化；无重叠。
- 21 个 APP 均可打开对应的原生占位页面，页面可以返回桌面。
- Room 保存桌面布局；有基本错误处理和最小构建检查。

之后再逐个增加本地数据功能、聊天 AI、可追溯记忆和双向事件互通。
